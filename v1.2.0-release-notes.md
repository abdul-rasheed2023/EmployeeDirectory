# Release v1.2.0 — Terraform-Managed VPC, ECR, IAM/IRSA, EKS, Ingress (Reproducible from Code)

**Date:** 2026-09-13
**Portfolio milestone:** Month 3 (per the 12-month dual-track plan) — network, registry,
compute, and IAM/IRSA now fully Terraform-managed and verified reproducible via a full
destroy/recreate cycle.

---

## What's In

### Infrastructure (Terraform)
- VPC with a deliberate multi-AZ CIDR plan: public + private-app + private-data subnets
  across 2 availability zones.
- Internet Gateway, NAT Gateway, and route tables with documented cost trade-off (NAT
  Gateway accepted at ~$32–45/month standing cost for this dev environment).
- ECR repository with lifecycle policy and scan-on-push.
- EKS cluster + managed node group, provisioned entirely from Terraform.
- IAM: separate cluster role, node role, and per-application IRSA roles — no shared
  over-privileged node-level access for application workloads (see ADR 0006).
- AWS Load Balancer Controller (via Helm) + Ingress, backing an ALB with health checks
  against `/health`.
- RDS MySQL 8.4 (Extended Support billing issue from a prior environment explicitly
  avoided by pinning `engine_version = "8.4"` ahead of provisioning).

### Application
- Employee Directory app running on EKS, 2 pod replicas, reading/writing to RDS via EF
  Core, with S3-backed photo storage and DynamoDB-backed metadata.
- **Fixed:** intermittent HTTP 400 on the Create-employee form, root-caused to an
  unshared, per-pod ASP.NET Core Data Protection key ring. Antiforgery tokens issued by
  one pod couldn't be decrypted by another when the ALB's round-robin routed a GET and
  its following POST to different pods.
- **Fix:** shared key ring via AWS Systems Manager Parameter Store
  (`Amazon.AspNetCore.DataProtection.SSM`), replacing an originally-planned but
  unsupported Secrets Manager approach (see ADR 0007 for the full trade-off analysis).
- Verified end-to-end: 15/15 real Create submissions, round-robined across both pods,
  returned successful `302` redirects with zero `400`s.

### Documentation
- `docs/adr/0006-iam-least-privilege.md` — IRSA design decision, including two real
  incidents encountered (stale kubeconfig post-recreate, EKS Access Entry policy scope
  mismatch).
- `docs/adr/0007-dataprotection-key-storage.md` — Parameter Store vs. Secrets Manager vs.
  EFS vs. Redis trade-off analysis and the pivot away from the original Secrets Manager
  plan.
- `docs/runbooks/eks-manual-recovery-steps.md` — every manual intervention required
  during this milestone's hands-on work, including a documented Terraform destroy
  limitation (see Known Issues below).

## Known Issues / Limitations

**`terraform destroy` does not complete cleanly in a single pass.** The `kubernetes` and
`helm` provider blocks are configured dynamically (`exec { command = "aws", args =
["eks", "get-token", ...] }`, sourced from `module.eks` outputs). During a full destroy,
this can fail outright at the start, or — as observed in this milestone's actual
destroy/recreate exercise — **abort partway through**, leaving cost-incurring resources
(VPC, NAT Gateway, EKS IAM roles/OIDC provider) orphaned in Terraform state while their
underlying AWS resources are in an inconsistent state relative to that record.

**Current documented workaround** (see the runbook for full detail): delete
Kubernetes/Helm-managed resources directly via `kubectl`/`helm` before running
`terraform destroy`, verify the ALB is actually gone via the AWS CLI, remove those
resources from Terraform state, then run `terraform destroy` for the remaining plain-AWS
resources. This was required *twice* in this milestone's actual teardown — once for the
Kubernetes-level resources, once again when the destroy silently died partway through
before reaching the network layer.

**This is not fixed in this release.** It's called out explicitly as a known limitation
rather than silently worked around, since it's a genuine reproducibility gap worth
addressing in a future milestone — either by restructuring provider configuration to not
depend on computed module outputs, or by adopting a documented, scripted two-phase destroy
as the permanent standard procedure.

## Verified Reproducibility (Day 38 exercise)

Full environment was destroyed and the process timed as evidence of genuine
infrastructure-as-code reproducibility (not "working because it was nursed into a good
state"):

- Destroy required 3 attempts due to the Kubernetes/Helm provider limitation above.
- Final successful destroy phase: **28 resources destroyed, 0 errors, 5 minutes**
  (NAT Gateway teardown alone: 42 seconds).
- Post-destroy verification confirmed zero lingering cost: no EKS clusters, no NAT
  gateways, no RDS instances, empty Terraform state.
